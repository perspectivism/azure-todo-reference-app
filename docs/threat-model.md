# Threat model

Scope: the deployed PoC (Blazor app, APIM, Function App, Cosmos DB, telemetry) and its deployment path. Structure: STRIDE category, threat, mitigations, residual risk.

| # | STRIDE | Threat | Mitigations | Residual risk (accepted) |
| --- | --- | --- | --- | --- |
| 1 | Spoofing / Elevation | **Unauthorized API access** without a valid token | APIM `validate-jwt` on every operation except `/health`; the Function validates issuer, audience, lifetime, signature, `tid`, `scp`, `oid` again; single-tenant registrations | `/health` is anonymous by design and returns no data |
| 2 | Information disclosure / Tampering | **Cross-user data access (IDOR)** by changing an id, URL, query, or body | Owner = token `oid`; `userId` never read from requests; partition-scoped point reads and queries; another user's item returns 404 like a missing one; unit and integration tests with two identities | None identified beyond a compromised user account |
| 3 | Spoofing | **Token theft or replay** | Short-lived v2 access tokens with audience and scope checks; HTTPS only; tokens kept server-side in the Blazor app (never sent to the browser) and never logged; in-memory token cache | A stolen token is usable by anyone until it expires (about an hour); no token binding |
| 4 | Information disclosure | **Secret exposure** in source, logs, or CI | No application secrets exist (managed identities, federated credentials, OIDC); `check-repo-safety.ps1` in the pre-commit hook and CI; emulator key detected by hash; no key-based auth on Cosmos or storage | The optional local Entra sign-in uses a developer-held client secret in user secrets |
| 5 | Tampering / Denial of service | **Input abuse** (oversized, malformed, or malicious payloads) | 16 KB body limit enforced before parsing; strict JSON types; length limits; generic problem responses; Razor output encoding | None significant for this data model |
| 6 | Denial of service | **Excessive API requests** | Unauthenticated calls rejected at APIM before reaching the Function; Function capped at 1 instance; serverless Cosmos and a budget alert bound cost | APIM Consumption has no per-key rate limiting, and subscription keys would conflict with the secretless design. An authenticated user (or a stolen token) can generate load and usage-based cost until noticed; budget alerts are delayed. |
| 7 | Spoofing / Elevation | **Direct access to the Function hostname**, bypassing APIM | The Function performs the full token validation itself; smoke tests check 401 at the Function hostname | APIM Consumption has no fixed outbound IP, so the hostname cannot be IP-restricted; requests with valid tokens can bypass APIM logging |
| 8 | Information disclosure | **Telemetry leakage** of tokens or user content | Logs carry ids only; tests assert titles, descriptions, and tokens are absent; APIM logs no headers/bodies/client IPs; KQL spot check in `docs/operations.md` | Entra object ids appear in logs as correlation keys (by design) |
| 9 | Elevation / Tampering | **Deployment credential compromise** | GitHub OIDC with a subject bound to repository + environment; no stored Azure secret; `todo-deployer` limited to one resource group and has no Graph permissions; optional environment reviewers; workflows pinned and least-privilege | A compromised repository/environment could redeploy or modify resources in that resource group (including role assignments within it) |
| 10 | Elevation | **Dev identity mode leaking into a deployed environment** | `Auth:Mode=Dev` only in `appsettings.Development.json` (not published); startup throws outside Development (tested); Bicep sets `Auth__Mode=Entra`; safety script rejects `'Dev'` in `infra/` | None identified |
| 11 | Repudiation | Actions not attributable | Request telemetry with correlation ids; structured logs with `UserId` for create/update/delete | Logs are subject to the daily cap and 30-day retention |

Review this table when adding routes, identities, or infrastructure.
